# NOTES — S08 · Party components

## Intent
The same party page as S07, split into pieces so the next person can change it without reading everything: `PartyList` holds the party and is the one place it changes, `PartyMember` is one card, and `Panel` is a box with a heading that I can reuse. It's for my friend who wants to add a Level up button and a Box panel, and for me next week when I have to find why a level came out wrong.

Prediction: A member's row → passing a prop, `<PartyMember {pokemon} />`, with `$props()` in the child. Who changes the party → a callback prop, `onremove`. What a member needs → `interface Props`. Add a Box panel → `children` and `{@render children()}`. After a remove → `$props.id()`, so each member's Remove button gets its own id and `PartyList` can find the next one to focus.

What it used: The first four matched. A member's row is `<PartyMember {pokemon} onremove={remove} onlevelup={levelUp} />` inside the `{#each}`, and the child takes them with `let { pokemon, onremove, onlevelup }: Props = $props();`. Who changes the party: two callback props, `onremove(pokemon.id)` and `onlevelup(pokemon.id)`, and only `PartyList`'s `remove` and `levelUp` touch `party`. What a member needs: `interface Props` at the top of `PartyMember.svelte`. The panel: `Panel.svelte` takes `title` and `children` and does `{@render children()}`, so `App` just writes `<Panel title="Party members"><PartyList /></Panel>`. After a remove, I was wrong. It's nothing from the table. It's the same plain JavaScript as S07 (`await tick()`, then `.focus()` on the next button), just moved into `PartyList`. Ids weren't needed because the position in the list is enough to find the next button. `$props.id()` did get used, but in `Panel`, to connect the `<section>` to its `<h2>` with `aria-labelledby`. I think I mixed up "an id for each thing" with "an id to find things with."

One line of `interface Props` read aloud, `onremove: (id: number) => void;`: "`onremove` is a function that takes a number, the Pokémon's id, and doesn't give anything back." The card calls it instead of changing the party itself because the card doesn't own the party. If it did `pokemon.level++` it would still work, but then there would be two places that change levels, and Svelte warns about it in the console. With a callback, the card only says what happened, and `PartyList` decides what to do.

## Accepted / changed / rejected
- Accepted: `PartyList` owns `party` (`$state`) and has the only two functions that change it, `remove(id)` and `levelUp(id)`. `levelUp` does `member.level += 1`, which is fine there because `PartyList` owns it. I searched `PartyMember.svelte` for `++`, `splice`, `filter`, and `=` on a prop: there are only the two callbacks. I pressed every button with the console open and got no warnings.
- Accepted: callbacks send the id, not the whole Pokémon, so `interface Props` can say `(id: number) => void`, which is short and easy to read.
- Accepted: every Pokémon starts at `level: 5`, added in `fetchPokemon`. PokéAPI doesn't have a level, so it's our own data, and it belongs where the party is made. I added the cap at 100 because levels in the games stop there.
- Accepted: the `<Panel>` goes in `App`, not inside `PartyList`. That way a Box panel next to it is one more `<Panel title="Box">` in `App`, and `PartyList` stays just the party.
- Wrote myself: `focusAfterRemove` (the `TODO(human)`). I started from my S07 one, but S07 used `querySelectorAll('button')`. Now every card has two buttons, so that would count Level up buttons too and focus the wrong one. I changed it to `.remove`. The other change: the "My party" heading is in `App` now, so `PartyList` can't reach it. When nobody's left, focus goes to "Your party is empty." (`tabindex="-1"`) instead. I think that's better anyway, because a screen reader says the party is empty instead of just the heading. I tested it keyboard only: removing Bulbasaur, then the next one each time, focus went Eevee, Snorlax, Pikachu, then the empty line.
- Changed: it wrote all three components before I looked at the page. It built clean and worked, but next time I'd make it stop after each one like the brief says, so if something broke I'd know which component did it.
- Changed: the styles from S07 got split up so each component has its own `<style>` (cards in `PartyMember`, the grid in `PartyList`, the banner in `App`), with the colors still as `:root` variables in `App` so they all match. Two buttons didn't fit side by side in a card, so they stack. Level up is a soft fill and Remove keeps the red outline, so they don't look like the same button.

## Dig deeper
`$bindable` (https://svelte.dev/docs/svelte/$bindable) lets a parent write `bind:pokemon={pokemon}` so the child is *allowed* to change the prop and the change flows back up. That's the "official" way to do what `pokemon.level++` does without the warning. I didn't need it because the whole point here was one owner: the card only reports, and `PartyList` changes. With `$bindable` there would be two places that can change the level again. I also read about `aria-labelledby` (https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-labelledby): it gives the `<section>` the name of its heading, so a screen reader can say "Party members, region." It needs an id that's unique on the page, which is why `$props.id()` matters if there are two Panels.
